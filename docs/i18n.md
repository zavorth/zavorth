# Internationalization (i18n)

Zavorth includes a native internationalization system that supports multiple languages across CLI, dashboard, desktop, and backend services.

## Supported Languages

| Locale | Language | Status |
|--------|----------|--------|
| `en-US` | English | Default, **complete** for product (including Trust Loop) |
| `pt-BR` | Portuguese (Brazil) | **Complete** for product (including Trust Loop) |
| Other locales under `src/i18n/locales/` | Various | Best-effort translations; may lag product keys |

Product-critical completeness for **en-US** and **pt-BR** is enforced by:

```bash
npm run i18n:check
# alias
npm run qa:i18n
```

Required namespaces checked today: `common`, `cli`, `desktop`, `trust-loop`.

## Device / OS locale (default)

When the user has **not** set an explicit product preference, Zavorth defaults to the device/OS locale.

### CLI and backend (`src/i18n/localeDetector.ts`)

Resolution order for environment-driven locale:

1. `ZAVORTH_LANG` (explicit process override)
2. `LC_ALL`
3. `LC_MESSAGES`
4. `LANG`
5. `LANGUAGE`
6. `USERLANGUAGE` / `USER_LANGUAGE` (Windows-friendly)
7. Fallback: `en-US`

Values are normalized (e.g. `pt_BR.UTF-8` → `pt-BR`, `en` → `en-US`).

```bash
# Force Portuguese
ZAVORTH_LANG=pt-BR zavorth start

# Force English
ZAVORTH_LANG=en-US zavorth start

# Auto-detect from system env (LANG / LC_*)
zavorth start
```

Config may also surface `zavorthLocale` from `ZAVORTH_LANG` via `src/config/sections/localeConfig.ts`.

### Zavorth Control (web dashboard)

Control uses `apps/zavorth-control-vite-shell/src/locale.ts`:

- Default preference is **`system`** (follow the browser / OS language via `navigator.languages` / `navigator.language`).
- Settings can override to a fixed supported locale (`en-US`, `pt-BR`, …) or keep `system` / `auto`.
- Overrides persist in **`localStorage`** under the Control locale key; if nothing is stored, Control follows the device language.

### Desktop app

Desktop ships surface strings in `apps/zavorth-desktop/src/i18n.ts` (en/pt objects). Language resolution uses `navigator.language` when no explicit language is passed (`resolveLanguage`). Trust Loop–related keys added for product surfaces stay in that file; full migration of desktop copy into YAML is **not** required for this pack.

### Settings override (honest behavior)

| Surface | Default | Override storage |
|---------|---------|------------------|
| CLI / services | OS env (`LANG` / `LC_*` / `ZAVORTH_LANG`) | Process env / config `zavorthLocale` |
| Control | System / device locale | `localStorage` preference (`system` or fixed locale) |
| Desktop | Browser/OS `navigator.language` | Call-site language argument when provided |

There is no single cross-surface settings file that always wins for every app; each surface resolves locale with the detectors above.

## Architecture

The i18n system is a singleton service (`ZavorthI18nService`) that:

- Lazy-loads YAML locale files per namespace
- Caches translations in memory
- Falls back through: requested locale → en-US → raw key
- Supports interpolation with `{variable}` syntax

### Permanent boundary: gateway HTTP JSON catalogs (`src/ai-gateway/i18n/`)

The AI gateway web surface keeps its own build-time JSON message catalogs
(`src/ai-gateway/i18n/messages/<locale>.json`, 32 locales) negotiated per HTTP
request through next-intl. This is a **permanent architectural boundary**, not
pending work:

1. next-intl requires statically analyzable `./messages/<locale>.json` imports
   at the server boundary so the framework bundles every locale into the
   server build; delegating lookups to the Node-side localization singleton
   would break that framework contract.
2. Most of the 32 gateway locales have no unified-system catalog; unifying
   today would silently drop coverage for those locales or force synthesizing
   20+ new catalogs.
3. Gateway negotiation is per-request (cookie → `x-locale` → `accept-language`);
   the unified system resolves one process-wide locale. Coupling them risks
   cross-request state bleed.

Unification may be revisited only if all three constraints change (framework
support for dynamic catalog providers, catalog coverage parity, and a safe
per-request locale context). See the JSDoc on `src/ai-gateway/i18n/request.ts`.

### Locale File Structure

```
src/i18n/
  locales/
    en-US/
      common.yaml      # App name, status words, actions
      cli.yaml          # CLI help text, errors
      errors.yaml       # Shared error strings
      services.yaml     # Backend service messages
      desktop.yaml      # Desktop app strings
      onboarding.yaml   # Setup wizard
      trust-loop.yaml   # Trust Loop product language
      ...
    pt-BR/
      (mirror of en-US/)
```

### Namespaces

| Namespace | Purpose |
|-----------|---------|
| `common` | App name, status, actions, time phrases |
| `cli` | CLI help, errors, command descriptions |
| `errors` | Shared error strings across all surfaces |
| `services` | Backend service messages (learning, scheduler, approvals) |
| `desktop` | Desktop app strings (YAML catalog) |
| `onboarding` | Setup wizard, quickstart flow |
| `trust-loop` | Trust Loop product language (ledger, risk budget, honesty, memory privacy, absorb, migration) |
| `telegram` | Telegram bot copy |
| `zavorthControl` | Control-oriented shared strings |
| `quickstart` | Quickstart flow |

Usage keys include the namespace prefix, e.g. `trust-loop.proof.ledger`, `common.app.name`.

## Usage in Code

### Direct Translation

```typescript
import { getI18nService } from '../i18n/index.js';

const i18n = getI18nService();

// Simple translation
i18n.t('common.app.name');  // "Zavorth"

// Trust Loop
i18n.t('trust-loop.proof.ledger');  // "Proof ledger"

// With interpolation
i18n.t('cli.welcome', { vars: { name: 'Ermy' } });  // "Welcome to Zavorth, Ermy."

// Check if key exists
i18n.has('common.app.name');  // true
```

### For CLI

```typescript
import { tCli, tCommon, tError } from '../i18n/cli.js';

tCli('welcome', { name: 'Ermy' });
tCommon('status.ready');
tError('provider.api_key_missing', { provider: 'OpenAI' });
```

### For Telegram

```typescript
import { t } from '../i18n/telegram.js';

t('auth.access_restricted');
t('scheduler.create_failed', { error: 'timeout' });
```

### For Desktop

```typescript
import { t, resolveLanguage } from '../../apps/zavorth-desktop/src/i18n.ts';

// Desktop uses en/pt in-memory maps (not full YAML migration)
t('proof.hubTitle');
t('riskBudget.chipLabel');
```

### Catalog Pattern (for services migrating from inline EN/PT)

```typescript
type MyServiceCatalog = { greeting: string; farewell: string };
const catalog = i18n.catalogFor<MyServiceCatalog>('services', ['greeting', 'farewell']);
// Returns typed object with translated strings
```

## Completeness check

```bash
npm run i18n:check
npm run i18n:check -- --json
```

Behavior:

1. Load en-US and pt-BR YAML for required namespaces
2. Flatten nested keys
3. Fail if any en-US key is missing in pt-BR
4. Fail if required Trust Loop keys are missing from en-US `trust-loop`
5. Print summary (ok / missing counts); exit `1` on failure

## Adding a New Language

1. Create directory `src/i18n/locales/<locale>/`
2. Copy all YAML files from `en-US/`
3. Translate each file
4. Add the locale to `KNOWN_LOCALES` in `src/i18n/types.ts` if it should be advertised
5. Update `normalizeLocale()` / `LOCALE_MAP` in `src/i18n/localeDetector.ts` to recognize the new locale

New locales remain **best-effort** until product completeness is intentionally expanded beyond en-US + pt-BR.

## Adding New Translations

1. Add keys to the appropriate `en-US/<namespace>.yaml` file
2. Add corresponding translations to `pt-BR/<namespace>.yaml`
3. Use the key in code: `i18n.t('namespace.key.subkey')`
4. Run `npm run i18n:check` for product namespaces
